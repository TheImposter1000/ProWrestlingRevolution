# Contracts reference screen acceptance specification

The two user supplied screenshots, each 1672 by 941 pixels, are the authoritative reference. They are not mood boards, suggestions, or general style guidance. The application must reproduce their structure and visual hierarchy as closely as possible within PWR's existing fixed logical window of 1366 by 768 pixels. The shared PWR header occupies the top 56 logical pixels. Both contract screens use the entire viewport underneath, with no left navigation rail. Build with real input controls and live MDB data, never by rendering the screenshot as one noninteractive picture.

## Screen 1. Worker Contracts selection

The top shared chrome reads "Contracts / Worker Contracts". The primary work area has one large cyan outlined navy frame with the slanted blue accent in the header. At its upper left are a white document icon and the large white "Worker Contracts" title. Directly below is the single italic sentence, "Select a contract to edit or create a new one." The upper right contains exactly one dark search field and exactly one dark "All Contracts" filter.

The table sits directly under these controls. Its columns, from left to right, must be Employer, Contract Type, Status, Begins, Expires, and Primary Role. The column headings are bold, white, and vertically centered on a dark blue metallic header with small sort chevrons. The employer column shows the real company logo when present and its initials. Contract Type uses a handshake or document marker. Status uses a colored circular status indicator and a human-readable label. Dates are formatted YYYY-MM-DD. Primary Role uses the worker's actual enabled contract role. A selected row is not a generic OS selection: it uses a bright full-width cyan outline and luminous blue interior, exactly like the middle row in the reference. Sorting, search, and Active/Expired filtering must not change the reference table geometry.

The table body remains tall even when only a few records exist; there is no compact card list. The foot strip is within the same frame and reads a live count such as "3 contracts (2 active, 1 expired)" at left. Its actions appear on one line at right in this order: Remove, Open, Add Contract. Remove and Open are dark blue beveled buttons with silver outlines and white icons. Add Contract is a more luminous cyan blue primary button with a plus icon. Double clicking a row opens the actual selected contract. The count is computed from the underlying records, not hard-coded from the screenshot.

## Screen 2. Contract Editor

The top shared chrome changes only its contextual subtitle to "Contracts / Contract Editor". Immediately under the chrome is one horizontal identity and biography frame. The far left contains the selected worker's portrait with a cyan outline and black caption strip. To its right are the Employee selector, Name field, and Short Name field, plus the Employer selector. The right side holds the Biography label and a full-width scrollable biography area. The identity row must not be replaced with a standalone profile card or with a left navigation menu.

Under that top row are four vertically aligned cards across the width, touching the same baseline. Card 1 is Basic Details and contains these rows in this order: Contract Type, Exclusive, Touring, Pay, On Loan, In Developmental, Iron Clad, Wage, Downside, Contract Begin, Expires In, Appearances Left. Card 2 is Roster Details and contains Alignment, Last Turn, Competes In, Brand, Division, Manager, Mask, Move Set, Momentum, Gimmick, Gimmick Basis, Gimmick Rating, Gimmick Status. Card 3 is Terms, Perks & Bonuses and contains Creative Control, Hiring Veto, Merchandise Cut, Wage Matching, Roster Usage, Intended Role, Shows Control, Bonus Type, Bonus Amount, Travel Cover. Card 4 is Roles and contains checkbox rows for Wrestler, Occasional Wrestler, Manager, On-Screen Personality, Play By Play Commentator, Colour Commentator, Referee, Road Agent.

Each card has a rounded thin neon cyan outline, deep navy body, bright steel blue gradient heading strip with angled graphic at the right, white topic icon, bold title, and small italic descriptive subtitle. The controls must be dark blue and thin silver-blue bordered, not standard unthemed white WinForms combo boxes. Labels are in a smaller bold white font. All rows are consistently spaced. The card layout must not wrap into one or two columns.

The bottom full-width footer contains two horizontal tools at left: "Import Details From Alter Ego" with a dark picker and Apply action, then "Copy Terms From Another Contract" with selectors and Apply action. At right are Reset and a bright primary Save. This occupies one common footer frame with cyan trim, not unrelated floating panels.

## Visual palette and backgrounds

The artwork is a dark almost-black indigo arena, with subtle blurred ring ropes and bright cyan accents. There are metallic blue header gradients, thin aqua outlines and slight neon bloom. White text has high contrast. The main layout should be visually comparable at the application's 1366 by 768 design resolution to a downscaled copy of each reference. Header geometry, card boundaries, column widths, row rhythm, field position, control colors, button sizing and footer placement are acceptance requirements. The real portrait and promotion logos must be read from the active picture pack when available. If a source image is absent, do not silently assume a particular wrestler or promotion.

## Functional and data requirements

The selection table shows the actual tblContract records associated with the selected tblWorker UID. Its company details resolve via tblFed. A selected existing contract opens Screen 2; Add Contract opens an unsaved draft; Remove uses confirmation and a database transaction. Saving updates the current contract and its tblContractBio in one transaction and checks for conflicting edits. Reset restores the selected record's original on-screen values. The employee's unrelated data must not be overwritten by contract saving. Date values must remain typed dates in MDB; numeric and yes/no fields must retain their database types. Names and images always come from the selected universe.

The current PRW tblContract schema does not contain LastTurn, GimmickStatus, CreativeControl, HiringVeto, MerchandiseCut, WageMatching, ShowsControl, BonusType, BonusAmount, or TravelCover. Their visible rows remain in the required locations. Until a separately reviewed schema extension exists, those rows are read-only and must not pretend they were saved. Imported TEW or unrelated MDB files must not be modified by this feature.

## Required verification

The Windows smoke run must compile both screens, assert that their live controls exist, capture worker-contract-list-preview.png and worker-contract-editor-preview.png, and make the images available as workflow artifacts. A successful compile is not a pixel-perfect visual signoff. A human must compare both images against the two supplied screenshots at the same display size, especially the search and filter controls, neon row highlight, card outlines, top portrait strip, equal-height card columns, and footer alignment. Do not merge or describe the result as exact until that visual comparison passes.
